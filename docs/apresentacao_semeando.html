Regra 1

Toda regra de negócio, validação e permissão fica no back-end. O front só ajuda o usuário.

Regra 2

Regra 3

Fluxo obrigatório router → service → repository → banco, verificado por teste automático.

Camadas de um módulo

Cada arquivo tem uma responsabilidade

Todo módulo tem a mesma estrutura. Um teste de arquitetura quebra o build se alguém pular uma camada.

router.pyRecebe a requisição, aplica require_roles(...), chama o service e devolve um schema. Sem regra de negócio.
permissions.pyQuem pode o quê no módulo, como tuplas de perfis reutilizáveis.
service.pyCasos de uso e regras de negócio. Não conhece HTTP: levanta exceções de domínio e faz o commit.
repository.pyÚnica camada que monta queries. Nunca faz commit.
models.pyEntidades SQLAlchemy 2.0 mapeadas para tabelas.
schemas.pyPydantic de entrada e saída. Nunca devolve um model direto. Entrada rejeita campos extras.

Módulos só conversam pelo service

Um módulo importa apenas service e schemas de outro, e o grafo de dependências não pode ter ciclos. Quando precisa reagir sem criar ciclo, usa eventos de domínio (core/events.py).

Transação por caso de uso

O service chamado pelo router faz o commit. Funções expostas para outros módulos participam da transação de quem chamou, como ocupar uma vaga ao aprovar a matrícula.

Funcionamento

Do clique ao banco, passo a passo

Exemplo: a secretaria aprova uma matrícula.

  1. Login e tokenPOST /auth/login devolve um access token JWT curto (15 min). O refresh token (7 dias) vai em cookie httpOnly e é rotacionado a cada uso. Senhas com Argon2.
  2. Perfil no routerDepends(require_roles(Role.ADMIN, Role.SECRETARIA)) responde 403 para quem não tem o perfil.
  3. Propriedade dos dadosO service confere o vínculo: um responsável só acessa filhos vinculados. Recurso de outra família responde 404, sem revelar que existe.
  4. Regra de negócio e máquina de estadosA transição de status passa por uma StateMachine. Transição inválida levanta InvalidTransitionError (409).
  5. Persistência e auditoriaRepository grava, service faz o commit e registra quem, quando e antes/depois em audit_log.
  6. Resposta padronizadaErros saem como {"detail": "...", "code": "..."}, sem stack trace.

Evento de domínio

O financeiro publica CobrancaPaga; quem se inscreve reage na mesma transação. O módulo que publica não conhece quem escuta.

Generics e composição

Máquina de estados reutilizável

Uma classe genérica serve a qualquer enum de status (matrícula, cobrança).

class StateMachine[S: Enum]:
    def can(self, current: S, target: S) -> bool: ...
    def ensure(self, current: S, target: S) -> None:
        if not self.can(current, target):
            raise InvalidTransitionError(...)

O que ainda é procedural, e a refatoração planejada

Os services e repositories são funções soltas e os models guardam só dados. Para ficar fiel ao conteúdo da disciplina, o plano é:

  • Modelo de domínio rico: mover regras para as entidades, como Cobranca.marcar_paga(), Cobranca.atualizar_atraso(hoje) e Bolsa.vigente_em(data).
  • Classes de serviço e repositório: BaseRepository[T] genérico e CobrancaService com a sessão injetada.
  • Strategy: PaymentGateway abstrata com FakeGateway e CoraGateway.
  • Hierarquia de pessoas: classe Pessoa com Aluno, Responsavel, Professor e Funcionario.

O que é tool calling

Em vez de só gerar texto, o modelo recebe a lista de funções disponíveis com seus parâmetros e devolve "chame a função X com estes argumentos". O sistema executa e devolve o resultado para o modelo continuar.

Onde vive

Módulo assistente da própria API, com 3 tabelas: conversas, mensagens e ações pendentes. Cada usuário só vê as próprias conversas.

Tool calling

O loop do agente

Implementado em assistente/service.py. Repete até o modelo responder só com texto, ou até um limite de passos.

  1. Monta o contextoSystem prompt do perfil do usuário + últimas mensagens da conversa + a lista de ferramentas que aquele perfil pode usar.
  2. Chama o LLMllm_client.chat(historico, tools) no formato chat/completions com tools.
  3. Veio texto?Salva a resposta e termina. Veio tool_calls? Segue para executar cada chamada.
  4. Valida a chamadaFerramenta existe e o perfil permite? Os argumentos passam no schema Pydantic? Se não, o erro volta ao modelo para ele corrigir.
  5. Consulta: executaChama o service do módulo com o usuário real, limita o tamanho do resultado e devolve ao modelo.
  6. Alteração: só propõeGera um resumo a partir do banco, grava uma ação pendente e para o loop. A resposta ao usuário traz os botões.
  7. Usuário confirmaO clique chama POST /acoes/{id}/confirmar, que revalida perfil e regras, executa e audita.

Segurança da IA

O modelo propõe, o servidor decide

Quatro garantias de projeto, todas no back-end.

1. O modelo nunca escreve

Ferramentas com mutates=True não são executadas pelo loop. Só o endpoint de confirmação, disparado por clique do usuário autenticado, executa.

2. Mesmas permissões da API

Tudo roda com o CurrentUser real. Como os services não checam perfil, cada ferramenta reaplica os perfis do módulo e o modelo só recebe as ferramentas do perfil.

3. Resumo vem do banco

O texto do cartão ("Aprovar matrícula #12 de Maria Souza, 3º ano") é montado pelo servidor, então o usuário percebe se o modelo errou um id.

4. Dado não é instrução

O prompt manda tratar o conteúdo devolvido pelas ferramentas como informação. Um aviso com "ignore as regras" não ganha poder de comando.

Uso único e expiração

A ação pendente confirma uma vez e expira em minutos. Segundo clique responde 409.

Argumentos congelados

O clique não aceita argumentos novos: executa exatamente o que foi mostrado.

Auditoria

Cada confirmação grava assistente.<ferramenta> em audit_log, distinguindo o que foi feito pelo assistente.

Dados sensíveis

CPF, ids de usuário e hashes são removidos do que o modelo recebe das ferramentas. Há limite de requisições por minuto e limite de passos do loop.
